# 05 复盘：最难的问题、收获与下一步

> 说明：本文由 AI 编程助手根据本次开发过程中的真实记录起草（问题、改动都能在代码、测试和 trace 中找到对应）。
> “学习收获”属于个人体会，候选人应按自己的实际理解修改，不要原样照抄。

## 1. 最难的问题

### 1.1 怎么让“满足时长”和“事实可追溯”成为可验证的事实，而不是模型的自述
模型很擅长说“已控制在 30 秒内”“所有信息均来自素材”，但这两句话本身不可信。最后的做法是三层：
1. **确定性工具**给结论：时长由公式算，合规由规则判，模型不能自评；
2. **版本指纹 + 提交闸门**：检查结果绑定到脚本内容指纹，`submit_script` 只接受同一版本两项都通过的脚本，改一个字就得重检；
3. **独立核对器**（`verify.py`）在运行结束后再用同一套代码重算一遍，逐镜核对“素材 ID - 时长 - 检查版本”。

难点在于第 2 层：一开始容易写成“检查过就算”，模型可能检查 v2、提交 v3。单测 `test_submit_different_version_than_checked_is_rejected` 专门守这一点。

### 1.2 规则检查的严格程度
太松会放过编造（“效率提升80%”），太严会让模型陷入反复修改。开发中真实遇到的例子：开头提问“还在手动打字幕？”被判“缺少来源”，但这只是描述痛点，不是产品宣称。最后引入“宣称词”（品牌名、支持、能、一键…）区分“宣称”和“提到话题”，前者阻断，后者只提示。数量词也做了中文数字识别（“八成”“两倍”），否则“效率提升八成”能绕过数字检查。

### 1.3 “模型决策”与“代码兜底”的边界
题目明确说固定条件分支、自动重试不算 ReAct。所以代码里刻意**不做**：检索为空不自动改写、超时不自动删句、工具失败不自动重试。代码只把结构化的观察（`count=0 + hint`、`over + 超出秒数 + 约需删减 N 字`、`retryable=true`）交给模型。护栏只做“不能做什么”（不能交未验证的稿、不能改用户给的时长、不能引用没检索过的素材、不能超过步数上限），不替模型做“该做什么”。

### 1.4 真实模型的行为和设计时的设想不一样
设计时以为“告诉模型超出多少秒”就够了，真实运行（[examples/deepseek-history/](../examples/deepseek-history/)）中却出现了：
- **贴着上限微调**：每次删一两个字，30.6 → 30.4 → 30.2 → 30.0，步数几乎耗尽；
- **说改了但没改**：decision_reason 写“这次真正合并两镜”，传入的脚本却和上一版完全相同，最多连续 6 次；
- **钻口径的空子**：把卖点挪进长字幕、口播只留关键词，让估算时长变短；
- **我对用例的假设也错了**：原以为 10 秒讲不完 4 个要点，模型写出了 47 字、正好 10.0s 的版本。

对应的修改都落在工具上（给出留余量的建议时长、对重复提交返回错误、字幕计阅读时间、必含要点不认角标），而不是在代码里替模型做决定。每次改动后都重跑真实模型对比效果，例如“只提示未修改”无效（仍重复 6 次），改成返回错误后才降到 1 次。

### 1.5 离线 Mock 本身也会有 bug
Mock 策略在“缩短开头钩子”一步会反复提交同一个版本，直到撞上单工具调用上限。这个 bug 反过来验证了上限护栏是有效的。也说明 Mock 只能证明流程，不能证明决策质量。

## 2. 收获（草稿，需本人修改）

- Agent 的可靠性主要来自工具与护栏的设计，而不是提示词：把“结论”交给确定性工具，把“选择”交给模型。
- 让模型在每次工具调用里填一句 `decision_reason`，既满足“记录决策依据”的要求，又不需要暴露或保存模型的内部思维。
- 接入具体模型前要读接口文档：DeepSeek 思考模式下带工具的多轮请求必须回传 `reasoning_content`，否则返回 400；系统里已有的 `OPENAI_BASE_URL` 会被 OpenAI SDK 自动读取，需要显式传 `base_url`。
- 测试要覆盖护栏本身（用预设工具调用序列的假模型），而不只是“跑通一次”。
- 真实模型的失败模式只有跑了才知道（贴边微调、重复提交、钻口径空子）；每次改动都要保留改动前的运行记录，用同样的输入重跑对比，才能说明改动有效。

## 3. 已知不足与下一步

| 不足 | 下一步 |
|---|---|
| 规则检查基于词表和数字匹配，无法识别同义改写（如“几乎不用手动改”这类隐含效果的说法） | 增加一个“事实核对”工具：对每个含事实的分镜，用模型做蕴含判断（句子是否被所引素材支持），结果仍由代码汇总并进入闸门 |
| 时长估算是经验公式（字数 ÷ 语速），没有考虑真实配音的语气停顿 | 接入 TTS 实测时长做校准，或按平台/风格积累实际成片时长回归参数 |
| 素材检索是关键词匹配 | 素材量大后改为向量检索 + 关键词混合，并保留“严格产品过滤”语义 |
| 真实模型结果有随机性，每个用例只跑了 1 次 | 每个用例重复运行 N 次，统计完成率、平均修订轮数、违规类型分布，作为回归评估 |
| `needs_input` 后需要重新运行 | 保存会话状态，支持用户补充后从断点继续 |
| 只有 CLI | 如有需要可加简单的 HTTP API 或可编辑的 Web 表格界面 |
