## 3. AI 开发过程中发现并修正的问题（有记录可查）

这些问题都是在“写完 → 运行 → 看 trace/测试失败 → 修改”的过程中暴露的，不是一次写对的：

| 问题 | 如何发现 | 修改 |
|---|---|---|
| Mock 压缩策略在“缩短开头”一步反复提交同一版本，直到撞上单工具调用上限 | 08 用例 trace 中 v4 连续出现 6 次，最终 `TOOL_CALL_LIMIT` | 每种压缩手段只用一次；同时证明了单工具上限这条护栏有效 |
| 必含要点“续航”无法被核对：M02 的事实原文里没有“续航”二字，只在关键词里 | 08 用例中 Mock 识别必含素材时漏掉 M02 | 修改合成素材原文，使事实文本本身包含要点词 |
| “必含要点 → 承载素材”匹配过宽：“降噪”同时命中 M02 的“关闭降噪”条件，导致所有素材都被当成必含、无法删减 | 01 用例意外返回 failed | 每个要点只取优先级最高的一条承载素材 |
| 规则过严：开头提问“还在手动打字幕？”被判 `MISSING_SOURCE` | 单测 `test_supported_script_passes` 失败 | 引入“宣称词”（品牌名/支持/能/一键…）：有宣称才算违规，只提话题降为提示 |
| `incomplete` 的原因文案不含“上限”，独立核对器判定不合格 | 场景测试 `10_step_limit` 失败 | 统一文案为“达到最大决策轮数上限 N” |
| DeepSeek 思考模式下，带工具的多轮请求必须回传 `reasoning_content`，否则 400 | 查阅 DeepSeek 官方文档 | 客户端保留并回传；默认关闭思考模式；trace 不记录思维内容 |
| 运行环境里已有 `OPENAI_BASE_URL`，OpenAI SDK 会自动读取，可能把请求发到别的服务 | 检查本机环境变量 | 客户端显式传入 `base_url` 与 `api_key` |

真实模型（DeepSeek）运行中发现、并经过“改代码 → 重跑 → 对比”验证的问题（证据在 [examples/deepseek-history/](../examples/deepseek-history/)）：

| 问题 | 证据 | 修改 | 效果 |
|---|---|---|---|
| 模型每次只删 1–3 字、贴着上限反复估算 | round1 的 01：30.6 → 30.4 → 30.2 → 30.0，用了 12/14 步 | 估算结果给出 `recommended_sec`（区间中部）和对应删减字数 | 01 降到 4 步；03b 由 failed 变为 completed |
| 模型声称已修改，实际原样重复提交同一版本 | round1 的 03b、06、08；round2 的 08 在提示“未修改”后仍重复 6 次 | 先加提示，仍无效后改为 `DUPLICATE_SUBMISSION` 错误并给出两个选项 | 08 的重复由 6 次降到 1 次 |
| 08 原本假设“10 秒放不下 4 个要点”，真实模型写出了 10.0s 的版本 | round1 的 08 | 用例改为 5 秒 6 要点（按口径最短 6.8s） | 用例真正覆盖“明确失败” |
| 模型把卖点挪进长字幕、口播只留关键词来压时长 | round2 的 `08_overtime_infeasible_after_dedup_fix`（5.6s） | 每镜取口播与字幕阅读时间较大值；必含要点不认角标小字 | 已生效（round3 起） |
| 首稿普遍偏长（30 秒目标首稿 34–38s） | round2 多个用例 | 首条消息给出“约 N 字旁白”的写稿参考 | round3 中 01 首稿 31.1s（round1 为 44.4s） |
| 建议“约删 17 字”，模型每次只删 2 字 | round3 的 09（26.2 → 25.7 → 25.5 → 25.1，撞上单工具上限） | 超时结果附逐镜删减建议 `cut_plan` | 最终 09：31.3 → 25.1 → 22.8s，8 步完成 |
| 08 再次可解：6 个要点全放进字幕、口播只留品牌名即可 4.8s；标题也被算作“包含要点” | round3 的 08 | 必含要点只认旁白/字幕；用例改为 3 秒 7 要点（最短 3.5s） | 最终 08：明确失败并给出冲突说明与 4 条建议 |
| 用户没提风格，模型把自己假设的风格写进简报（风格决定语速口径） | round4 的 03b | `update_brief` 只接受能在用户回答中找到依据的值 | 最终 03b 风格作为假设写进风险 |

最终运行结果与对比见 [03-evaluation.md](03-evaluation.md)。

## 6. 第二次复查（2026-11-11，Codex）

我委托 Codex 从 GitHub 已发布的 `ccd334a` 版本出发，检查仍有改进空间的地方，落实修复，再用我的视角补充 AI 使用说明和复盘。这轮的代码、测试、验证执行和文档补写由 Codex 完成；下表记录的是工具实际做过和验证过的工作。

| 复查发现 | 本轮改动 | 验证方式 |
|---|---|---|
| 同一稿件先按默认口径检查，再补上平台或风格，仍能拿旧结果提交；先检查、后取到所引素材时，同稿重检又会被当成重复 | 关键字段缺失时拒绝提交；简报或相关素材变化时，只作废受影响的检查。脚本版本号保留，旧检查仍可在 trace 中追溯 | 预设工具序列复现小红书超长标题和慢语速超时；验证旧检查不能提交、同版重检能给出正确结论 |
| 时长只做数字子串匹配，用户回答“120 秒”也能填成 20 秒；非对象工具参数和异常分镜字段可能打断循环 | 时长填写要求回答中的明确秒数（或仅由数字构成的回答）；畸形参数返回结构化错误，模型仍能继续调用工具 | 对照真实数字、年龄数字和畸形 JSON 的回归用例 |
| 批量用例能用 `case_id` 写到 `--out` 之外，或让两个用例写到同一个目录；用例还能抬高命令行上限 | 批量启动前验证用例和输出目录，拒绝空批次；用例只能收紧执行预算 | 对越界路径、同名目录、无效输入和命令行预算跑离线回归 |

- **离线证据**：新增 22 个回归用例。Python 3.14 下 `92 passed, 1 skipped`（默认跳过既有 live 测试）；Python 3.11 下重新跑了 12 个 Mock 用例。原 25 份存档及下述新样本合计 26 份，均通过 [独立核对](../examples/verification_report.md)。核对器复用业务规则，还不能作为独立的事实或成片质量评审。
- **真实 API 证据**：只重跑 `03b_missing_info_answered` 一次。DeepSeek 尝试填入未确认的风格，工具拒绝写入；模型随后完成稿件。共 6 轮决策、7 次工具调用，预计 18.5 秒（目标 20 秒）。[运行记录](../examples/review-2026-11-11/03b_missing_info_answered/trace.md) · [脚本输出](../examples/review-2026-11-11/03b_missing_info_answered/output.md)。这次调用验证了补充信息后的正常路径；先检查再修改简报等反例由预设工具序列覆盖。没有在新代码上重跑整套真实模型用例。
